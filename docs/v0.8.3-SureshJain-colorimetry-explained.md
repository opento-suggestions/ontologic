# v0.8.3 Colorimetry Ontology — Suresh & Jain Semantic Grounding

## Citation

Merugu Suresh & Kamal Jain. "Semantic Driven Automated Image Processing using the Concept of Colorimetry." *Procedia Computer Science* 58 (2015) 453-460.

- DOI: [10.1016/j.procs.2015.08.062](https://doi.org/10.1016/j.procs.2015.08.062)
- Conference: Second International Symposium on Computer Vision and the Internet (VisionNet'15)
- License: CC BY-NC-ND 4.0

## What This Is

The Suresh-Jain paper defines a color ontology in OWL that classifies color models (RGB, CMYK, HSB, HSL, LAB, XYZ) under a shared class hierarchy and connects them through three relations: `HasCoordinate`, `IsDividedInto`, and `HasProperty`.

Ontologic v0.8.3 uses this ontology as **semantic grounding** for proof-of-reasoning. We don't store the OWL graph on-chain. Instead, each rule and proof carries an immutable reference to the ontology, and the integer color coordinates from the paper's data properties are hashed directly into the RIOM binding. The cryptographic receipt proves that reasoning was executed *according to that specific semantic definition*.

## The OWL Class Hierarchy

From Figures 3 and 5 in the paper (Protege class tree and OWL directed graph):

```
Thing
  Quality
    Colour                          (abstract parent class)
      ColourLayoutDescriptor         }
      ColourQuantizationDescriptor   } HasProperty relation (Colour -> Descriptors)
      ColourSpaceDescriptor          } [not yet modeled]
      ColourStructureDescriptor      }
      DominantColourDescriptor       }
      ColourModes                    (parent of all color models)
        RGB                          ── v0.8.3 MVP
        CMYK                         ── v0.8.3 MVP
        HSB                          ── not yet
        HSL                          ── not yet
        LAB                          ── not yet
        XYZ                          ── not yet (root of all colorimetry)
```

Key structural fact: **color models are sub-classes of `ColourModes`, not direct sub-classes of `Colour`**. The descriptors are siblings of ColourModes under Colour. This is visible in Figure 5's directed graph: `Colour -> ColourModes -> {RGB, CMYK, ...}`.

## Three OWL Relations

The paper defines three class relations (Section 5):

### 1. HasCoordinate

> "Describes the relation between color and color space value."

**Ontologic implementation**: Integer color coordinates embedded as `properties` on bundle inputs and outputs. These get canonicalized (RFC 8785) and hashed into `inputsHash` and `outputsHash`, sealing the colorimetric values into the RIOM binding.

```json
{
  "inputs": [{
    "tokenSymbol": "CYAN",
    "properties": { "cmyk_c": 100, "cmyk_m": 0, "cmyk_y": 0, "cmyk_k": 0 }
  }],
  "output": {
    "tokenSymbol": "BLUE",
    "properties": { "cmyk_c": 100, "cmyk_m": 100, "cmyk_y": 0, "cmyk_k": 0 }
  }
}
```

The `transform@v1` operator makes this explicit: input carries RGB coordinates, output carries CMYK coordinates, and the `bindingHash` proves the mathematical transform between color spaces.

**Scales**: RGB uses 0-255 (per paper Section 3.2: "trichromatic color gamut"). CMYK uses 0-100% (per paper Section 3.2: "colorimetric color space ranges from 0 to 100%").

### 2. IsDividedInto

> "Describes the relation between color and colormodels."

**Ontologic implementation**: Two capstone `classify@v1` proofs that seal the class hierarchy:

- `sphere://demo/ontology/colourmodes-isdividedinto-rgb` — proves ColourModes contains RGB
- `sphere://demo/ontology/colourmodes-isdividedinto-cmyk` — proves ColourModes contains CMYK

Evidence: the RGB and CMYK domain proofs themselves. If R+G=Y, G+B=C, and R+B=M all have valid proofs on HCS, then the RGB color model is demonstrably active in the system.

### 3. HasProperty

> "Describes the relation between color and Descriptors."

**Not yet modeled.** This connects Colour to its descriptors (Layout, Quantization, Structure, Dominant, Scalable). These are image-processing metadata properties, not color-model reasoning. The schema has room for them: future phases can add `property` fields to bundles and `HasProperty` relation to `semantics`.

## The `semantics` Object

Every RuleDef carries a `semantics` field that anchors it to the OWL ontology:

```json
{
  "semantics": {
    "ontology": "doi:10.1016/j.procs.2015.08.062",
    "classPath": "Thing.Quality.Colour.ColourModes.CMYK",
    "class": "CMYK",
    "inputsRef": ["CMYK", "CMYK"],
    "outputRef": "CMYK",
    "relation": "HasCoordinate"
  }
}
```

| Field | Purpose |
|-------|---------|
| `ontology` | DOI of the grounding paper |
| `classPath` | Full OWL hierarchy path (from Thing to leaf) |
| `class` | Short class name for the color model |
| `inputsRef` | Which OWL classes the inputs belong to |
| `outputRef` | Which OWL class the output belongs to |
| `relation` | Which of the three OWL relations this rule enacts |

This object gets hashed into the RuleDef's `contentHash` (keccak256 of canonical JSON). Once published to HCS, the ontological reference is immutable.

## How the Triune Architecture Enforces Semantic Grounding

### Peirce (Logic)

The `bindingHash` links integer-typed inputs to integer-typed outputs under a specific OWL-grounded ruleUri. If an agent attempts to process a CMYK-grounded rule with RGB additive logic, the `inputsHash` will diverge (because the `properties` carry different coordinate values), and the binding becomes invalid.

### Floridi (Meaning)

The MorphemeProof anchored to PROOF_TOPIC carries the `ruleId`, which resolves to a RuleDef containing the `semantics` field. Any verifier can trace back: this proof was executed under `Thing.Quality.Colour.ColourModes.CMYK` using the `HasCoordinate` relation from the Suresh-Jain ontology.

### Tarski (Material)

Token metadata stamps commit to a hash chain computed from semantically-grounded proof data. The BLUE token's provenance root is permanently inscribed with a proof that was calculated using `cmyk_c: 100, cmyk_m: 100, cmyk_y: 0, cmyk_k: 0`.

## CMYK Transform Graph

Each of the 8 base colors has a `transform@v1` proof that bridges from RGB coordinates to CMYK coordinates:

```
RED     RGB(255,0,0)     --> CMYK(0,100,100,0)
GREEN   RGB(0,255,0)     --> CMYK(100,0,100,0)
BLUE    RGB(0,0,255)     --> CMYK(100,100,0,0)
YELLOW  RGB(255,255,0)   --> CMYK(0,0,100,0)
CYAN    RGB(0,255,255)   --> CMYK(100,0,0,0)
MAGENTA RGB(255,0,255)   --> CMYK(0,100,0,0)
WHITE   RGB(255,255,255) --> CMYK(0,0,0,0)
BLACK   RGB(0,0,0)       --> KEY CMYK(0,0,0,100)
```

The `inputsHash` seals the RGB coordinates. The `outputsHash` seals the CMYK coordinates. The `bindingHash` proves the transform under the `HasCoordinate` relation.

## Not Yet

These are protocol hooks, not omissions. The schema is ready; only the data needs to grow.

| Feature | Paper Reference | Schema Hook | When |
|---------|----------------|-------------|------|
| **XYZ root** | "root of all colorimetry" | `classPath: Thing.Quality.Colour.ColourModes.XYZ` | v0.9+ |
| **HSB, HSL, LAB** | Sub-classes of ColourModes | Same classPath pattern, new transform@v1 edges | v0.9+ |
| **HasProperty** | Colour -> Descriptors | `relation: "HasProperty"` in semantics | v1.0 |
| **Chromaticity diagram** | Fig. 8c | XYZ (x,y) coordinates as properties | v0.9+ |

The protocol doesn't need to change. Only the data needs to grow.

## Bug Fix: Chunked Message Resolution

During this session, a bug was discovered and fixed in `scripts/v0.7/lib/resolve.js`. When batch publishing creates chunked HCS messages (>1KB), the chunks can be interleaved with other messages (registry entries). The original resolve function assumed chunks were at adjacent sequence numbers.

**Fix**: Bounded bidirectional search. When a chunked message is hit, search backward and forward from the hit point for sibling chunks with the same `initial_transaction_id`. Capped at 8 mirror node queries to stay under 10 total per resolve call.
